# AdaptiveMLOps - Phase 2 Report

## Objective
Expose the trained ML model through a production-style FastAPI prediction API with validation, latency measurement, confidence scores, request tracing, and persistence in PostgreSQL.

## Implementation Details

1. **Prediction API (/api/v1/predictions):**
   - Built a robust API endpoint that abstracts the offline ML artifact.
   - Requires rigorous PredictionRequest Pydantic models (enforcing valid strings and text size constraints).
   - Standardized PredictionResponse format including confidence, generated predictions, request trace IDs, execution latency, and exact model version.
   
2. **Database Migration & Persistence:**
   - Introduced a Prediction SQLAlchemy model (in ackend/app/db/models/prediction.py) capturing every inference generated by the API.
   - Successfully authored and generated Alembic migrations representing this initial table.
   - Engineered the prediction_repository.py layer to manage writing prediction inferences directly into PostgreSQL efficiently.
   
3. **Model Inference Engine (prediction_service.py):**
   - The API is strictly locked to initialize its PredictionService exclusively using the configured PRODUCTION_MODEL_DIR.
   - Client requests cannot spoof or select arbitrary model artifacts; production routing acts as a secure boundary.
   - Inferences intelligently extract internal Scikit-Learn predict_proba probability max values to determine numeric statistical confidence.
   - Records execution latency accurately using Python's 	ime.perf_counter().

4. **Reliability & Consistency:**
   - HTTP standard 503 is returned if the model artifact cannot be successfully loaded at runtime (protecting API resilience).
   - Auto-generates missing HTTP X-Request-Id headers to strictly trace client calls.

5. **Test Automation:**
   - Authored complete test coverage in 	est_predictions.py.
   - Simulated an in-memory SQLite dependency for SQLAlchemy DB dependency overrides.
   - Verified valid payloads, handled 422 Unprocessable Entity rejections for empty strings or 5000+ length attacks.
   - Verified 503 Service Unavailable handling if model offline.
   - Proved proper prediction schema mapping and database row persistence.

## Post-Review Refinements (Resolved Issues)

1. **Architectural / Model Loading:**
   - Moved ML model loading to a FastAPI async lifespan context manager in main.py. This ensures it's properly executed during event-loop startup instead of a synchronous import execution, which is best practice.
2. **Security / Rate Limiting:**
   - Implemented slowapi rate limiting across the create_prediction endpoint, restricted to 10 requests/minute, to prevent Denial of Service (DoS) since ML inference is expensive.
3. **Database Constraints:**
   - Refactored created_at in the DB model to use Postgres-native server_default=func.now() for deterministic timing at the DB level, preventing python clock-drift issues. Updated the Alembic migration directly.
4. **Testing Infrastructure:**
   - Introduced a docker-compose.test.yml to spin up an ephemeral PostgreSQL test database. This solves test DB divergence since the local SQLite test suite doesn't flawlessly replicate Postgres behaviors (e.g. native UUID, constraints).
